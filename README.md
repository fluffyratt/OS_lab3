# Лабораторна: кеш, доступ до пам'яті, false sharing і синхронізація

## Вимоги
Linux, GCC із C11, make, Python 3, matplotlib (`python3 -m pip install matplotlib` за потреби). Код компілюється **мовою C**. Python використовується **лише для візуалізації**.

## Запуск у терміналі з каталогу `cache_lab`
```bash
make                # компіляція
make quick          # коротка перевірка (~ швидше, дані переписуються)
make run            # повний запуск, 5 повторів кожної конфігурації
```
Після цього `results/raw.csv`, `results/summary_median.csv`, `plots/*.png`.

## Призначення дослідів
1. `working_set`: 4 KiB–64 MiB; послідовне читання проти залежного випадкового pointer chasing. Міряємо наносекунди на доступ. Sequential має апаратну передвибірку і незалежні завантаження, random pointer chasing її обмежує.
2. `stride`: масив 8/32 MiB, крок 8–2048 байтів; міряємо вартість доступу. Великий stride зменшує корисне використання cache line.
3. `matrix`: `C=A*B` звичайним `ijk` (читання стовпця B) і з попереднім транспонуванням B (послідовне читання). Міряємо GFLOP/s. **Час транспонування не включений** у вимірюваний час множення — це обмеження методики, яке треба зазначити.
4. `false_sharing`: різні atomic-лічильники поруч проти кожного в окремій 64-byte структурі. Міряємо мільйони інкрементів/с. 64 байти — типова, але не гарантована на всіх CPU, довжина cache line.
5. `sync`: thread-local, atomic `fetch_add`, mutex, а також навмисно некоректна з погляду атомарності складеної операції пара `atomic_load` + `atomic_store`. Міряємо частку збережених інкрементів. Ця пара не породжує C data race, але демонструє **логічну race condition (lost update)**. Не плутати atomic окремих операцій з атомарністю `counter++` як цілого.
6. `volatile`: один потік, інкремент volatile-змінної. Volatile **не** забезпечує міжпотокової синхронізації, захисту від гонок чи еквівалентності atomic.

## Важливі умови коректності
- Фіксуйте CPU, кількість ядер, компілятор, версію ОС, cache sizes та частоту CPU.
- Повторіть повний запуск; виконуйте без фонового навантаження й на тій самій машині.
- `CLOCK_MONOTONIC` дає часову тривалість, а не число hardware cache misses.
- `perf stat -e cache-references,cache-misses ./cache_lab --quick` — **опціонально**. Події є апаратними/платформними проксі, не точними лічильниками L1/L2/L3 для кожного тесту. Доступ може бути заборонено налаштуваннями Linux. У цьому запуску всі тести змішані, тому perf підсумовує їх; для ізольованої оцінки потрібен окремий режим кожного тесту.
- У `sync` оптимізатор може швидко виконувати thread-local операції; порівнювати час цих режимів як рівноправну вартість синхронізації не можна. Основний показник графіка — **коректність**, а не швидкість.
- CSV-файли в архіві — **приклад короткого запуску в тестовому середовищі**, а не вимірювання вашого ПК. Перед звітом запустіть `make run` у себе.
